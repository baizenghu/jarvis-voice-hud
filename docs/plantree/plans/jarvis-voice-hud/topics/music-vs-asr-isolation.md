# 主题 —— 放歌不得干扰语音识别(KWS + STT)的分层防御

**硬约束(用户明确要求)**:歌曲外放的声音**不能影响语音识别**——既不能让 STT 把音乐当语音转写,
也不能让持续音乐淹没/误触 KWS 唤醒。

关键杠杆:音乐在 **HUD webview 内播**(decisions/0006)→ HUD **100% 知道何时在放歌、且持有 audio 元素的音量/暂停控制**。
这是"听音时静音音乐"能做到确定性的根本(mpv 原生进程方案给不了这个信号)。

## 两个受害面,分开治
- **STT(对话轮)**:唤醒后录用户说话做转写。音乐混进来 → 转写全是垃圾。
- **KWS(唤醒)**:`kws_listener.py` 独立进程持续听麦。音乐外放进麦 → 误触发 / 淹没"贾维斯"。

## 分层防御(从确定性强到兜底)

### Layer 1 —— STT 听音窗暂停/重压音乐(必做,确定性,易)
进入对话录音窗的瞬间,HUD `audio.pause()`(或音量压到 ~0),录完用户语音、转写完再恢复。
- **保证**:STT 绝不和音乐混 → STT 受害面**彻底解决**。
- 代价:放歌中对话时音乐顿一下/变小——可接受,且是 HUD 自己持有 audio 元素,确定性触发。
- 落点:`voice/audio.ts` 录音开始/结束钩子里 pause/resume 音乐元素。

### Layer 2 —— KWS 唤醒期 OS 级回声消除(解决"放歌中还能喊醒")
KWS 持续听,音乐外放必进麦 → 用**操作系统回声消除**,以扬声器输出为参考信号消掉它:
- **家里 Linux**:PipeWire/PulseAudio `module-echo-cancel`(WebRTC AEC),产出"已消回声"虚拟源,
  让 `kws_listener` 监听该虚拟源而非原始麦 → 音乐 + TTS 都被参考信号抵消。**不改 KWS 引擎**(决策 0003 不动)。
- **Windows**:优先麦克风/声卡自带 AEC;不行则退 Layer 3。
- 真机要调:AEC 对持续音乐的压制是否够 KWS 不误触/不漏听。

### Layer 3 —— 应用层兜底(AEC 不可用 / 不够时)
- **放歌持续 duck**:音量降到既能听又不至于盖过"贾维斯";HUD 持有音量,确定性。
- **KWS 自适应**:网关知道正在放歌(它代理流),把"放歌中"状态推给 `kws_listener`,
  放歌时收紧阈值防音乐误触(复用 Phase 3 的 busy/idle 经 `/api/events` 上报机制)。
- **末位兜底**:放歌中唤醒可靠性下降是已知代价 → 点击小球/物理键唤醒。

## 验收门(Phase 4 M4)
两台真机:放一首鼓点强的歌,期间①喊"贾维斯"能醒(Layer 2/3)②醒后对话转写干净(Layer 1)③"停"退场。

## 残留未决(收窄后)
- Windows 侧 OS AEC 走哪条(声卡自带 vs 软件方案)。
- 家里 `module-echo-cancel` 对外放音乐的实测压制效果(够不够 KWS 不误触、不漏"贾维斯")。
